# パーティクル描画の仕組み

作成日時: 2026-06-13 02:06
更新日時: 2026-06-13 06:40

## 概要

このアプリの風パーティクル描画は、通常は `src/renderer/gpu-particles.ts` の `GpuParticleSystem` が担当する。WebGL2 と `EXT_color_buffer_float` が使えない環境では、`src/renderer/particles.ts` の `ParticleSystem` にフォールバックする。

GPU 版の理解としては、「パーティクルを描画し、フレームバッファを暗くし、その上にまた描画する」を繰り返している、で概ね正しい。ただし、暗くしているのはメイン画面そのものではなく、軌跡専用のオフスクリーン描画先である。また、現在位置は線ではなく点として描かれ、点の時間的な蓄積によって流線のような軌跡を作っている。

## 描画ループ

`src/renderer/main.ts` のアニメーションループでは、おおまかに次の順で処理する。

1. `controls.update()` などでカメラと地図要素を更新する。
2. `gpuParticles.update(camera)` で、粒子状態と軌跡テクスチャを更新する。
3. `renderer.render(scene, camera)` で、地球、海岸線、国境線、星空、UI 以外の通常シーンを描画する。
4. `gpuParticles.composite()` で、軌跡テクスチャを画面上に合成する。

このため、GPU 版のパーティクルは Three.js の通常シーン内に直接置かれているのではなく、いったん軌跡用テクスチャに描かれたあと、最後にメイン画面へ重ねられる。

## GPU 版のバッファ

GPU 版では、主に 2 種類の ping-pong バッファを使う。

- 状態バッファ: `stateRead` / `stateWrite`
- 軌跡バッファ: `trailRead` / `trailWrite`

状態バッファは `RGBA32F` 相当の浮動小数テクスチャで、各画素が 1 粒子を表す。中身は `(lon, lat, age, maxAge)` で、経度、緯度、年齢、寿命を持つ。

軌跡バッファは画面サイズの `RGBA` テクスチャで、前フレームまでに描かれたパーティクルの残像を保持する。こちらは見た目のための画像であり、粒子の物理状態そのものではない。

## 1. 粒子状態の更新

`GpuParticleSystem.update()` の最初で、`UPDATE_FS` シェーダーを全面クアッドに対して実行し、`stateRead` から読んだ状態を `stateWrite` に書き込む。

このシェーダーでは、現在の `(lon, lat)` に対応する風ベクトルを `uWind` テクスチャからサンプリングし、経度と緯度を進める。寿命を超えた粒子や極付近へ行きすぎた粒子は、地球上のランダムな位置に再配置される。

更新後に `stateRead` と `stateWrite` を入れ替える。これにより、次フレームでは今回書いた状態が読み取り元になる。

## 2. 軌跡バッファの減衰

次に、軌跡用の `trailWrite` を描画先にする。

まず `FADE_FS` シェーダーで、前フレームまでの軌跡画像である `trailRead.texture` を読み、色を `uFade` 倍して `trailWrite` にコピーする。`uFade` は 1 に近いほど軌跡が長く残り、低いほど早く消える。

つまり「フレームバッファを暗くする」という理解は、この軌跡バッファに対しては正しい。メイン画面全体を暗くしているわけではない。

実装では `floor(c * 255.0 * uFade) / 255.0` としており、8bit バッファでも残像がいつまでも薄く残り続けないよう、少しずつ確実に 0 へ落ちるようにしている。

## 3. 現在の粒子を上書き描画

減衰コピーのあと、同じ `trailWrite` に `pointsScene` を描く。

`pointsScene` には、色を書かない深度専用の地球メッシュと、粒子の `THREE.Points` が含まれている。先に地球の深度だけを描き、その後で粒子を描くことで、地球の裏側にある粒子が深度テストで隠れる。

粒子の頂点シェーダー `POINT_VS` は、状態テクスチャから各粒子の `(lon, lat)` を読み取り、3D 球面上の点へ変換する。フラグメントシェーダー `POINT_FS` は、風速に応じた色をランプテクスチャから選び、寿命の始まりと終わりでは透明度を下げる。

ここで描かれるのは「線分」ではなく「現在位置の点」である。点が毎フレーム少しずつ移動し、前フレームの点が減衰しながら残るため、結果として流線のように見える。

描画後、`trailRead` と `trailWrite` を入れ替える。これで次フレームでは、今回の軌跡画像が前フレーム画像として使われる。

## 4. メイン画面への合成

通常シーンを `renderer.render(scene, camera)` で描いたあと、`GpuParticleSystem.composite()` が呼ばれる。

`composite()` は `trailRead.texture` を全面クアッドで画面に描く。マテリアルは `AdditiveBlending` なので、地球や海岸線の上に軌跡の色が加算合成される。

軌跡バッファ内では、地球そのものは描かれない。軌跡バッファには残像と現在の粒子点だけが入り、最後にメイン画面へ重ねる。

## 移流: 進む向きの計算

粒子は「自分の現在地でベクトル場(風)を読み、その向きへ一歩進む」という前進積分(前進オイラー法)で動く。`UPDATE_FS` の中身はおおむね次の通り。

1. 現在の `(lon, lat)` を風テクスチャ `uWind` の格子座標へ変換し、`windAt()` で風 `(u, v)` をサンプリングする。テクスチャは線形フィルタなので、格子の間も GPU のバイリニア補間で空間的に滑らかに読める。
2. 経度・緯度を進める:
   - `lon += u * k / cos(lat)`
   - `lat += v * k`
   - `k`(`uK`)は「風 1 m/s あたり 1 フレームで何度進むか」の係数で、`BASE_DEG_PER_FRAME × 速度倍率`。
   - `cos(lat)` で割るのは、高緯度ほど経度 1 度の実距離が短くなるため(子午線の収束補正)。
3. 経度は日付変更線をまたいで `mod` でラップする。

つまり粒子は固定の軌道を持たず、毎フレームその場の場を見て向きを決め直す。

## 色: 現在地の風速

粒子の色は「その粒子が今いる場所の風速」を毎フレーム計算して決める。

- 頂点シェーダー `POINT_VS` で `vSpeed = length(windAt(現在地))` を求める(位置依存・毎フレーム再計算)。
- フラグメントシェーダー `POINT_FS` で、その速さをカラーランプ `uRamp`(左下の凡例と同じ配色)へ通す。`clamp(vSpeed / RAMP_MAX_SPEED, 0, 1)` で 0〜35 m/s に対応づけ、上限は頭打ち。

そのため 1 つの粒子でも、遅い領域では寒色、ジェット気流など速い領域では暖色〜赤へと連続的に変化する。軌跡(蓄積バッファ)には毎フレームその時の色の点が焼き込まれるので、1 本の流線の中で色がグラデーション状に変わる(頭が現在速度、尾ほど過去の速度)。

## 長時間でも破綻しない理由

単純な移流を長時間回しても破綻しないのは、いくつかの仕掛けによる。

- **寿命と再配置(最重要)**: 各粒子は `maxAge`(ランダム)で寿命が尽きると、球面上で一様ランダムな位置へ再配置される(`asin` 一様サンプリングで極偏りを防ぐ)。これがないと粒子が収束帯に溜まって団子になり、他が空く。常に湧き直すことで密度が均一に保たれる。`|lat| > 85` でも再配置し、極の特異点を避ける。
- **出現・消滅のフェード**: `vLife = clamp(min(age/8, (maxAge-age)/24))` で、誕生直後と寿命間際は暗くする。再配置は瞬間的なテレポートだが、消える時も湧く時も暗いので、画面にワープの線が走らない。
- **蓄積バッファによる軌跡**: 線分で粒子をつないでいないため、テレポートしても古い軌跡は減衰して消えるだけで不自然な直線が残らない。
- **数値的な安定化**: 1 フレームの歩幅が小さい、`cos(lat)` に下限クランプ(`max(…, 0.05)`)で極での発散を防ぐ、経度ラップ、極での再配置。これらにより前進オイラーでも破綻しない。

## 風場の差し替え・時間アニメーション

`setWind()` / `setWindInterp()` は風テクスチャ(と格子情報の uniform)を差し替えるだけで、粒子の状態(位置・寿命)には一切触れない。粒子は次フレームに新しい場をサンプリングして現在地から流れ続けるので、コマを切り替えても動きが途切れない。

時間補間を有効にすると、隣接 2 コマの `u/v` を補間して場が時間的にも滑らかにモーフィングする(`writeWindInterp`)。結果として粒子が見る速度は空間・時間の両方で連続に変化し、向きも色も急にジャンプしない。

## カメラ操作中の減衰

カメラが動いている間は、残像が画面空間に貼り付いたように見えやすい。そのため、カメラ行列の変化を検出した場合は `MOVING_FADE` を使い、軌跡を通常より速く減衰させる。

カメラ停止後は、`currentFade` をゆっくり `trailFade` へ戻す。急に明るさが変わって見えないようにするためである。

## CPU フォールバックとの違い

CPU 版の `ParticleSystem` は、GPU 版とは描画方式が違う。

CPU 版では、各粒子について経度、緯度、寿命、軌跡点列を JavaScript の配列で持つ。毎フレーム、粒子位置を CPU で進め、軌跡点列を 1 つずつずらし、`THREE.LineSegments` の `position` と `color` を更新する。

つまり CPU 版は「前フレーム画像を暗くして残す」方式ではない。軌跡の長さは、配列に保持する点数そのもので決まる。負荷を抑えるため、CPU 版では粒子数と軌跡点数が GPU 版より控えめに制限されている。

## まとめ

GPU 版の実態は、次の流れである。

1. 風テクスチャを読んで、状態バッファ上の粒子位置を更新する。
2. 前フレームの軌跡画像を少し暗くして、新しい軌跡バッファへコピーする。
3. その上に現在の粒子点を描く。
4. 軌跡バッファをメイン画面へ加算合成する。

したがって、「パーティクルを描画、フレームバッファを暗くする、その上に描画、を繰り返している」という理解は、GPU 版の軌跡表現についてはほぼ正しい。より正確には、「メイン画面とは別の軌跡用フレームバッファで、前回の軌跡を暗くしてから現在の粒子点を描き足し、それをメイン画面に合成している」と言える。
